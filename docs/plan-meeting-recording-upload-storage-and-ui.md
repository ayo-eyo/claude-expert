# Plan: Загрузка и хранение записи встречи + интерфейс встречи

**PRD**: docs/prd-meeting-recording-upload-storage-and-ui.md
**Дата**: 2026-08-10

> Примечание: во фронтенд-приложении (`apps/frontend`) сейчас нет тестового фреймворка (jest/RTL) — только `lint`/`typecheck`. PRD не просит добавлять тестовую инфраструктуру, поэтому в фазах 3–4 «тесты» — это конкретные ручные сценарии проверки по acceptance-критериям PRD, а не автотесты. Бэкенд-фазы (1–2) используют существующий e2e-стек Jest/Supertest (`apps/backend/test/*.e2e-spec.ts`).

## Фазы реализации

### Фаза 1: Backend — схема записи и загрузка файла

**Цель**: Владелец встречи может загрузить файл записи; файл валидируется, сохраняется на диск и появляется в БД со статусом `uploaded`. Это минимальный рабочий путь (tracer bullet) всей фичи.
**Затрагивает**: database, backend

**Задачи:**

- [ ] Добавить модель `MeetingRecording` в `apps/backend/prisma/schema.prisma` (`id`, `meetingId` уникальный, `originalName`, `mimeType`, `sizeBytes`, `storagePath`, `status`, `uploadedAt`), каскадное удаление при удалении `Meeting`; выполнить миграцию и регенерацию клиента
- [ ] Модуль хранения файлов: корневой каталог из env, генерация имени файла на сервере (не из пользовательского ввода), запись файла на диск, удаление файла при откате
- [ ] `POST /meetings/:id/recording`: multipart-загрузка, `JwtAuthGuard` + проверка владельца через существующий паттерн `findOneForOwner`, whitelist MIME (`video/mp4`, `video/webm`, `audio/mpeg`, `audio/wav`, `audio/webm`), лимит размера файла, создание записи со статусом `uploaded`
- [ ] Обработка ошибок эндпоинта: 409 при уже существующей записи, 400 при недопустимом MIME, 413 при превышении лимита; во всех случаях ошибки — гарантированная очистка частично записанного файла на диске
- [ ] e2e-тесты (`recordings.e2e-spec.ts`): 201 + файл физически на диске; 400 недопустимый MIME (файла на диске нет); 413 превышение лимита (файла на диске нет); 404 при встрече чужого владельца; 401 без JWT; 409 при повторной загрузке

**Когда готова**: `POST /meetings/:id/recording` работает end-to-end (валидный файл → 201, метаданные, файл на диске), все перечисленные e2e-тесты зелёные, `npm run test -w backend` проходит.

### Фаза 2: Backend — чтение, скачивание, удаление и интеграция со списком встреч

**Цель**: Полный жизненный цикл записи на бэкенде: получить метаданные, скачать файл, удалить запись; поле `recording` доступно в существующих ответах по встречам.
**Затрагивает**: backend

**Задачи:**

- [ ] `GET /meetings/:id/recording`: метаданные записи (без бинарника), 404 если записи нет или встреча не принадлежит пользователю
- [ ] `GET /meetings/:id/recording/download`: отдача файла с диска с корректными `Content-Type` (из сохранённого `mimeType`) и `Content-Disposition: attachment; filename="<originalName>"`
- [ ] `DELETE /meetings/:id/recording`: удаление записи из БД и файла с диска в порядке, исключающем «мёртвую» ссылку в БД на несуществующий файл; 204 при успехе
- [ ] Добавить поле `recording: MeetingRecordingResponse | null` в `MeetingResponse`, обновить `MeetingsService.toResponse` и include-запросы для `GET /meetings` и `GET /meetings/:id`
- [ ] e2e-тесты: `GET` метаданных (200 и 404); `download` отдаёт байты, идентичные исходному файлу, и верный `Content-Disposition`; `DELETE` → 204, повторный `GET` → 404, файла нет на диске; `GET /meetings` и `GET /meetings/:id` возвращают `recording: null` без записи и объект метаданных с записью

**Когда готова**: все 4 эндпоинта записи и оба эндпоинта встреч покрыты e2e-тестами и зелёные, `npm run test -w backend`, `npm run lint -w backend`, `npm run typecheck -w backend` проходят.

### Фаза 3: Frontend — страница встречи

**Цель**: У встречи появляется отдельная страница с деталями, доступная по клику из списка; обрабатываются состояния загрузки, ошибок, 404 и просроченной сессии. Это tracer bullet для фронтенда — работает без загрузки файлов.
**Затрагивает**: frontend

**Задачи:**

- [ ] `lib/api.ts`: добавить `getMeeting(token, id)` с обработкой 404 через `ApiError`; расширить тип `MeetingResponse` полем `recording: MeetingRecordingResponse | null`
- [ ] Страница `apps/frontend/src/app/meetings/[id]/page.tsx`: загрузка встречи по id, отображение заголовка, даты, списка/количества участников
- [ ] Состояния страницы: спиннер при загрузке, alert при ошибке запроса, отдельный экран «встреча не найдена» при 404, редирект на `/login` при 401 (по аналогии с `apps/frontend/src/app/page.tsx`)
- [ ] На `/` сделать карточку встречи кликабельной (`next/link` на `/meetings/[id]`)
- [ ] Ручная проверка по сценариям PRD: клик по карточке открывает корректную страницу; открытие чужого/несуществующего id даёт «не найдено»; открытие с просроченным токеном ведёт на `/login`

**Когда готова**: переход из списка на страницу встречи работает, на странице верно отображаются title/дата/участники, 404 и редирект на `/login` воспроизводятся вручную, `npm run lint -w frontend`, `npm run typecheck -w frontend` проходят.

### Фаза 4: Frontend — загрузка, отображение, скачивание и удаление записи

**Цель**: На странице встречи можно загрузить запись, увидеть её статус, скачать и удалить — полный пользовательский путь фичи.
**Затрагивает**: frontend

**Задачи:**

- [ ] `lib/api.ts`: `uploadRecording` (XHR с отслеживанием прогресса и поддержкой отмены), `deleteRecording`, `downloadRecording` (запрос с заголовком `Authorization`, сохранение blob с исходным именем файла — без `<a href>`)
- [ ] Компонент загрузки: выбор файла кнопкой и drag-and-drop, клиентская валидация MIME-типа и размера до отправки запроса, индикатор прогресса в процентах, кнопка отмены
- [ ] Компонент отображения записи: имя файла, размер в человекочитаемом виде, дата загрузки, чип статуса, кнопки «Скачать» и «Удалить»
- [ ] Интеграция в `/meetings/[id]`: пустое состояние (блок загрузки) ↔ состояние с записью, обновление без перезагрузки страницы через локальный state; удаление возвращает к пустому состоянию
- [ ] Ручная проверка по сценариям PRD: успешная загрузка и появление данных без reload; отклонение неверного типа/размера без сетевого запроса; отмена загрузки не создаёт запись; скачивание сохраняет исходное имя файла; удаление убирает запись и позволяет загрузить новую

**Когда готова**: полный сценарий «загрузка → просмотр → скачивание → удаление» воспроизводится в браузере согласно всем acceptance-критериям PRD по UI, `npm run lint`, `npm run typecheck`, `npm run test` проходят на корне репозитория.
