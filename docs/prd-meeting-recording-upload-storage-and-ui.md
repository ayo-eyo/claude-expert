# PRD: Загрузка и хранение записи встречи + интерфейс встречи

**Дата**: 2026-08-10
**Статус**: Draft

## Цель

Дать владельцу встречи возможность прикрепить к ней файл записи (видео/аудио), чтобы запись хранилась вместе со встречей и была доступна для скачивания. Файл получает статус обработки — это задел под будущий пайплайн транскрипции, который в этой итерации не реализуется.

## Пользовательские сценарии

- Пользователь кликает по карточке встречи в списке -> попадает на страницу `/meetings/[id]` с деталями встречи и блоком записи
- Пользователь выбирает файл записи (drag-and-drop или через кнопку) -> видит прогресс загрузки в процентах
- Загрузка завершилась -> в блоке записи появляется имя файла, размер, дата загрузки и статус `uploaded`
- Пользователь нажимает «Скачать» -> получает исходный файл записи
- Пользователь загружает файл неподдерживаемого типа или больше лимита -> получает понятную ошибку до/во время загрузки, запись не создаётся
- Загрузка прервалась (сеть, отмена) -> запись не появляется в блоке, частичный файл не остаётся на диске, пользователь может повторить
- Пользователь удаляет загруженную запись -> запись исчезает из блока, файл удаляется с диска, можно загрузить новую
- Пользователь открывает встречу, к которой запись уже загружена -> видит текущую запись и её статус, кнопка загрузки заменена на «Заменить»/«Удалить»
- Пользователь открывает `/meetings/[id]` чужой встречи -> получает 404

## В скоупе

**Данные**

- Модель `MeetingRecording` в Prisma: `id`, `meetingId` (уникальный — одна запись на встречу), `originalName`, `mimeType`, `sizeBytes`, `storagePath`, `status`, `uploadedAt`
- Статусы записи: `uploaded`, `processing`, `ready`, `failed`. В этой итерации файл после успешной загрузки получает `uploaded` и остаётся в нём — переходы статусов не автоматизируются
- Каскадное удаление записи при удалении встречи (на уровне схемы)

**Backend**

- `POST /meetings/:id/recording` — multipart-загрузка файла, только для владельца встречи
- `GET /meetings/:id/recording` — метаданные записи (без бинарника)
- `GET /meetings/:id/recording/download` — отдача файла с корректными `Content-Type` и `Content-Disposition`
- `DELETE /meetings/:id/recording` — удаление метаданных и файла с диска
- Поле `recording` (метаданные или `null`) в ответах `GET /meetings` и `GET /meetings/:id`
- Валидация: MIME-тип из белого списка (`video/mp4`, `video/webm`, `audio/mpeg`, `audio/wav`, `audio/webm`), максимальный размер файла, повторная загрузка при существующей записи отклоняется с 409
- Хранение на локальной файловой системе: настраиваемый через env корневой каталог, имя файла на диске генерируется сервером (не берётся из пользовательского ввода)
- Очистка частично записанного файла при неуспешной загрузке

**Frontend**

- Новая страница `/meetings/[id]`: заголовок, дата, участники, блок записи
- Переход на страницу по клику на карточку встречи в списке на `/`
- Компонент загрузки: выбор файла кнопкой и drag-and-drop, прогресс в процентах, отмена загрузки
- Отображение загруженной записи: имя файла, размер в человекочитаемом виде, дата загрузки, чип статуса, кнопки «Скачать» и «Удалить»
- Клиентская валидация типа и размера до старта загрузки
- Состояния страницы: загрузка данных, ошибка запроса, 404 для чужой/несуществующей встречи, пустое состояние блока записи
- Редирект на `/login` при 401, как на существующих страницах

## Не в скоупе

- Реальная обработка файла: транскрипция, резюме, извлечение длительности, генерация превью, чексуммы
- Автоматические переходы статусов, фоновые задачи, очереди, воркеры
- Несколько файлов на встречу, произвольные вложения (документы, презентации, изображения)
- S3/MinIO и любое внешнее объектное хранилище
- Возобновляемая (chunked/resumable) загрузка и загрузка напрямую в хранилище по presigned URL
- Встроенный плеер записи в браузере — только скачивание
- Доступ участников встречи к записи (сейчас в API нет доступа участников даже к самой встрече)
- Вирус-сканирование, антифрод, квоты на пользователя
- Редактирование и удаление самой встречи

## Технические ограничения

- Локальное хранилище привязывает бэкенд к конкретной машине: горизонтальное масштабирование и контейнерные перезапуски без volume приведут к потере файлов. Осознанное ограничение итерации; миграция на объектное хранилище должна быть возможна заменой одного слоя доступа к файлам
- Загрузка идёт через процесс NestJS, тело запроса ограничено лимитом размера. Большие записи (сотни МБ) упираются в таймауты и память Node — лимит размера файла обязателен и должен быть согласован на клиенте, в сервере и в прокси, если он появится
- В `MeetingsService` доступ к встрече везде фильтруется по `ownerId` (`findAllForOwner`, `findOneForOwner`). Эндпоинты записи обязаны использовать ту же проверку, иначе появится расхождение в правах доступа
- Prisma-схема лежит в `apps/backend/prisma/schema.prisma` с генерацией клиента в `src/generated/prisma` — новая модель требует миграции и регенерации клиента
- Файловая система и БД не транзакционны: удаление метаданных и файла может рассинхронизироваться. Порядок операций должен исключать «мёртвые» ссылки в БД на несуществующий файл
- Каталог хранения не должен быть доступен статикой напрямую — отдача файла только через авторизованный эндпоинт
- Фронтенд использует HeroUI v3 и Next.js 16: компоненты берутся из `@heroui/react` v3 API, `HeroUIProvider` не существует
- Токен хранится на клиенте и передаётся заголовком `Authorization` — скачивание нельзя сделать простой ссылкой `<a href>`, нужен запрос с заголовком

## Критерии готовности

- [ ] `npx prisma migrate` создаёт таблицу записи; повторная загрузка при существующей записи возвращает 409
- [ ] `POST /meetings/:id/recording` с валидным mp4 возвращает 201 и метаданные со статусом `uploaded`; файл физически лежит в настроенном каталоге
- [ ] `POST /meetings/:id/recording` с файлом вне белого списка MIME возвращает 400, файл на диск не попадает
- [ ] `POST /meetings/:id/recording` с файлом больше лимита возвращает 413, частичный файл на диске не остаётся
- [ ] `POST`/`GET`/`DELETE` записи для встречи чужого владельца возвращают 404
- [ ] Все четыре эндпоинта записи без валидного JWT возвращают 401
- [ ] `GET /meetings/:id/recording/download` отдаёт байты, идентичные загруженному файлу, с исходным именем в `Content-Disposition`
- [ ] `GET /meetings` и `GET /meetings/:id` возвращают поле `recording`: `null` без записи, объект метаданных с записью
- [ ] `DELETE /meetings/:id/recording` возвращает 204, после него `GET` записи даёт 404 и файла нет на диске
- [ ] Клик по карточке встречи на `/` открывает `/meetings/[id]` с корректными title, датой и количеством участников
- [ ] На `/meetings/[id]` без записи виден блок загрузки; после успешной загрузки без перезагрузки страницы появляются имя файла, размер, дата и чип статуса
- [ ] Во время загрузки отображается прогресс в процентах и работает отмена; после отмены запись не создана
- [ ] Выбор файла неподдерживаемого типа или превышающего лимит показывает ошибку в UI без сетевого запроса
- [ ] Кнопка «Скачать» на странице встречи сохраняет файл с исходным именем
- [ ] Кнопка «Удалить» убирает запись из UI и возвращает блок в состояние загрузки
- [ ] Открытие `/meetings/[id]` с несуществующим id показывает состояние «встреча не найдена», а не пустой экран или ошибку рантайма
- [ ] Просроченный токен на `/meetings/[id]` приводит к редиректу на `/login`
- [ ] `npm run lint`, `npm run typecheck`, `npm run test` проходят на корне репозитория
